01 · Producto

Un CRM compartido,
datos separados

AmbarCRM ayuda a empresas a atender conversaciones de WhatsApp y organizar contactos, oportunidades, agentes y automatizaciones.

Una sola instalación sirve a muchas empresas. Cada empresa tiene su organización, usuarios y datos; los módulos se habilitan según sus necesidades.

Ejemplo · clínica

Pacientes + Citas

Expedientes y agenda adecuados a su operación.

Ejemplo · tienda

Productos + Caja

Inventario y ventas dentro del mismo CRM.

La web configura y opera el CRM. La app móvil acerca la bandeja y el chat al teléfono del agente.

08 · Modelo de cobros

Cada cliente cobra
con su propia cuenta

1

Conecta su cuenta

Cada empresa autoriza su Mercado Pago o su Stripe desde Configuración → Módulos → Pagos en línea.

2

El dinero va directo

El pago llega a la cuenta de la empresa. Ámbar Rojo no recibe ni custodia fondos, y así evitamos responsabilidades de dinero ajeno.

3

El CRM concilia

Webhooks firmados marcan el pago, y desde la venta se pueden hacer reembolsos. Las credenciales se guardan cifradas.

Pendiente de diseñar: IVA por producto y qué hacer con la comisión de la pasarela. El cliente podrá absorberla o trasladarla como cargo visible. Lo fiscal se valida con un contador antes de ofrecerlo.

10 · Concepto clave

Multi-tenant: compartir instalación,
aislar cada empresa

1

org_id

Identifica qué empresa es dueña de cada fila.

2

RLS

PostgreSQL filtra y valida filas según el tenant activo.

3

Rol crm_app

La conexión de la app queda sujeta a las políticas RLS.

Ejemplo: si la sesión pertenece a Clínica Norte, la petición establece su organización como contexto; PostgreSQL devuelve las filas de esa empresa. Aunque alguien olvide agregar un filtro a una consulta, RLS vuelve a limitar las filas.

Error típico: conectarse como dueño de la BD o crear una tabla sin tenant/política. Las claves foráneas no sustituyen el aislamiento. Código: web/src/lib/db.ts.

11 · Conceptos técnicos en sencillo

Qué hace cada pieza
del stack web

Next.js

Sirve páginas y también recibe peticiones API. Por eso web y backend viven en el mismo proyecto.

TypeScript

Añade tipos al JavaScript. Ayuda a detectar, antes de ejecutar, que una función reciba datos con forma incorrecta.

PostgreSQL

Guarda organizaciones, usuarios, contactos y conversaciones en tablas relacionadas.

Prisma

Traduce operaciones del código a consultas de base de datos y describe modelos en el esquema.

API

Es el contrato para pedir o cambiar datos. Ejemplo: “dame la bandeja de esta sesión”.

RLS

Es una regla de PostgreSQL que limita qué filas puede ver o cambiar la conexión actual.

No es necesario dominar todo el stack para una tarea pequeña; sí entender qué capa se está modificando.

16 · Cómo se comunica la app

Tres canales, tres trabajos

01

Bearer · identidad

Al iniciar sesión, el backend entrega un token. La app lo guarda en almacenamiento seguro y lo adjunta a cada petición para demostrar quién es.

Si el token no sirve, el servidor responde 401 y la app vuelve al login.

02

SSE · en vivo

Es una conexión abierta del servidor hacia la app. El servidor avisa que hubo un cambio y la app vuelve a pedir los datos actualizados.

Es como dejar una línea abierta para recibir avisos mientras la app está activa.

03

FCM · en segundo plano

Firebase envía una notificación al teléfono cuando el sistema operativo suspende la app y SSE ya no está conectado.

Al tocarla, la app puede abrir la conversación indicada.

El sistema operativo puede cerrar SSE cuando la app pasa a segundo plano. Por eso push complementa el tiempo real; no es el mismo mecanismo.

17 · De tocar Enviar a ver el mensaje

¿Qué sucede al mandar un mensaje?

1 · La persona escribe

La pantalla del chat entrega el texto a su estado (ChatProvider).

2 · La app hace la petición

El repositorio llama al endpoint de mensajes. ClienteApi añade el Bearer de la sesión.

3 · El backend valida

La API comprueba sesión, organización y permisos; después ejecuta la operación con el canal conectado.

4 · La base guarda

PostgreSQL conserva el mensaje bajo la organización activa y RLS mantiene el aislamiento.

5 · Tiempo real avisa

SSE avisa a las sesiones conectadas para que refresquen la conversación.

6 · Push si hace falta

Si el móvil está en segundo plano, Firebase puede entregar la notificación push.

Este recorrido explica las piezas; la entrega real depende del canal y la configuración del ambiente.

21 · Inicio

Una primera PR chica

Backend + web

  1. Leer README, módulos, multi-tenant, despliegue y API móvil.
  2. Preparar Node, Docker y variables locales ficticias.
  3. Levantar BD desechable.
  4. Seguir una ruta API hasta reglas/Prisma.
  5. Correr checks de lint, tipos y tarea.
  6. Crear rama y PR con evidencia.

App Flutter

  1. Leer AGENTS, CONTRIBUTING y arquitectura.
  2. Instalar Flutter y Android Studio.
  3. Ejecutar flutter pub get.
  4. Pedir acceso a demo-meta y Firebase si hace falta.
  5. Probar login y bandeja en entorno de prueba.
  6. Elegir una pantalla, correr analyze/test y abrir PR.

Ambos proyectos: rama por tarea, PR pequeño y revisión de Julio. En Flutter se exige prueba en dispositivo Android real para la tarea terminada.
