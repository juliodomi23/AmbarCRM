# Decisiones de canales

## Desconexión de Messenger · 17-oct-2026

- El DELETE del canal Messenger cancela primero `/{pageId}/subscribed_apps` mediante
  `messengerGraph`, con token en Authorization y timeout existente de cinco segundos.
  Solo después del resultado remoto permitido se ejecuta el borrado local.
- `success:true` devuelve `desuscrito:true`. Un token 190/sesión invalidada o una
  página no disponible (HTTP 404, código 803 o 100/subcódigo 33) permiten retirar
  el canal local con `desuscrito:false` y motivo fijo. Esto no confirma revocación
  de credenciales ni una desuscripción efectiva en Meta; 100/33 puede representar
  un objeto inaccesible, no prueba por sí solo que se haya eliminado la página.
- Red, timeout, 429/5xx y errores no clasificados devuelven 502 fijo y conservan
  canal e histórico. 429/5xx prevalecen sobre el código de error del cuerpo.
  No se registran ni retornan tokens o mensajes de error externos.
- Se conserva el contrato de `borrarDatos`: histórico por defecto; eliminación
  solo si el administrador la elige y se permite retirar el canal. Los errores
  temporales nunca eliminan conversaciones aunque se hubiera elegido borrarlas.
- La UI usa el Confirmador existente en dos pasos: cancelar la primera pregunta
  aborta, la segunda ofrece borrar o conservar. Solo aparece en canales Messenger
  existentes dentro de la configuración de administrador; el servidor exige
  `requireSesion(true)` y el acceso a datos sigue sujeto a RLS.
- WhatsApp y API no cambian. No se modifica el webhook, la firma ni los envíos.
  Se prueba con Graph simulado: éxito, historial, errores definitivos y temporales,
  reintentos, 401/403, aislamiento 404 y ausencia de secretos en respuestas/bitácoras.
  La prueba HTTP verifica login real, botón y borrado con conservación del histórico.

## Login de Facebook para Messenger · 16-oct-2026

- Se comparte `cargarFacebookSdk` con Embedded Signup de WhatsApp. El ID de app para Messenger viene del servidor (`META_APP_ID`); no se recibe del formulario. Si el SDK ya usa otro ID, la conexión falla con aviso. No se modifica el webhook de Messenger ni su firma.
- El primer clic prepara la conexión y carga el SDK; el segundo llama a `FB.login` sin esperar peticiones, conservando el gesto del usuario para abrir el popup. Se solicita `code`, siguiendo el patrón de WhatsApp. No se usa un callback OAuth propio ni se coloca el código en una URL del CRM.
- Permisos: `pages_show_list,pages_messaging,pages_manage_metadata`. No se agrega `pages_read_engagement`: únicamente se descubre la lista de páginas administradas y sus campos básicos mediante `/me/accounts`, sin leer publicaciones ni engagement. Nombre/foto y permisos efectivos quedan pendientes de comprobar con una app real; la foto es opcional. Si Meta rechaza permisos, se ofrece la conexión manual sin ampliar scopes silenciosamente.
- La tabla `messenger_login` conserva las páginas y sus tokens en un único valor cifrado con AES-GCM (`encryptMetaToken`). Tiene `org_id` con DEFAULT, RLS y GRANT explícitos, además de un vencimiento de diez minutos desde el inicio, sin renovación al listar. Se prefiere a una cookie con tokens porque una cuenta puede administrar muchas páginas y superar su límite de tamaño.
- La cookie `ambar-messenger-login` solo contiene un identificador aleatorio; es `httpOnly`, `SameSite=Strict`, `Secure` en producción y limitada a las dos rutas. Su autenticidad se comprueba buscando el intento con hash de `state`, empresa, usuario y hash del token de sesión NextAuth. Copiar la cookie o el estado a otra sesión no permite utilizarlos. El estado anti-CSRF se devuelve al cliente, se pasa al SDK y se verifica en el header `x-messenger-state` en los dos POST posteriores. El SDK administra además su propio retorno OAuth; no dependemos de que su callback devuelva `state`.
- Ambos endpoints exigen `requireSesion(true)`, Origin exacto del CRM, JSON, límite de tamaño y rate limit por admin/empresa e IP. La preparación también se limita. Iniciar otro intento invalida el anterior de esa sesión. Solo se devuelven `{ id, nombre, foto }`; la foto debe ser HTTPS de CDN de Meta y carecer de parámetros de credenciales. Los tokens de usuario solo viven durante el intercambio.
- El canje corto y largo usa POST con credenciales en el cuerpo. Graph recibe tokens en Authorization. La paginación reconstruye la URL con el cursor y nunca sigue `paging.next`, que puede incluir credenciales. Los errores de Meta se sustituyen por mensajes fijos; no se devuelve ni registra su cuerpo, ni siquiera parcialmente.
- Listar reclama el intento una sola vez; conectar lo consume mediante DELETE condicional antes de validar y suscribir la página. Dos conexiones concurrentes del mismo intento no crean dos canales. Se borra tras éxito o fallo del intercambio; un fallo después de consumirlo exige preparar otra conexión. Los intentos abandonados se rechazan al vencer y sus filas se purgan al iniciar otra conexión de esa empresa. La caducidad lógica siempre se verifica, aunque la fila aún exista.
- Se reusa `guardarCanalMessenger` con el ID existente encontrado bajo RLS para reconectar sin duplicar. Se conserva su control global de páginas activas y su 409, incluido el índice UNIQUE para carreras entre empresas. Los canales con `appId` o `appSecretEncrypted` propios se rechazan tanto al preparar como al conectar; el formulario manual permanece disponible.
- Una autorización conecta una página. Para otra página, se prepara una nueva conexión; cada canal conserva su token independiente. Esto evita mantener credenciales temporales después de conectarse.
- Evidencia y límites de validación: [informe de pruebas del 16-oct-2026](pruebas-messenger-login-facebook-2026-10-16.md).

## Decisiones previas de canales

- Se conserva `canales_whatsapp` como tabla de bandejas para mantener las relaciones y la API v1. `wa_message_id` representa el identificador de cualquier proveedor; su unicidad es por canal. Un trigger deriva `mensajes.canal_id` de la conversación para cubrir también los envíos existentes de WhatsApp.
- Messenger/API identifican al contacto por `(canal_id, identificador_externo)` (índice parcial SQL). WhatsApp sigue identificando por teléfono dentro de la empresa. No se deduce que dos personas sean la misma a partir de un nombre o PSID.
- Si una identidad externa recibe después un teléfono libre en esa empresa, se agrega al mismo contacto: una futura conversación WhatsApp reutiliza ese contacto, sin perder el PSID/id externo. Si el teléfono ya pertenece a otro contacto, se conserva la identidad y no se fusionan historiales automáticamente; el teléfono de ese evento no sustituye al existente. La consolidación manual de contactos queda fuera de alcance.
- Prisma representa las columnas del índice parcial como campos normales: el índice y las funciones/triggers se administran exclusivamente mediante SQL.
- En la fase base los proveedores API/Messenger devuelven un error explícito hasta completar sus respectivas fases; no se pueden crear desde la interfaz todavía.
- API: una entrega inicial más hasta tres reintentos adicionales (500/1000/2000 ms) solo para red, timeout, 429 y 5xx. Identificador de entrega y cuerpo estables; timestamp y firma se recalculan por intento. Los receptores deduplican por entrega. La resolución DNS se valida en cada intento y la conexión TLS fija la IP pública validada.
- La creación de contacto, conversación, mensaje y contador ocurre en una transacción con bloqueo del canal. Las llamadas externas se ejecutan después del commit. Duplicados concurrentes no repiten dispatch, lead ni bienvenida. No hay cola durable nueva: un cierre abrupto entre guardar y los efectos externos conserva el mensaje, pero puede omitir estos efectos; es el límite del pipeline actual.
- API recibe medios por URL HTTPS y puede entregar archivos cargados desde el chat como data URI, conservando una copia local privada. Sus credenciales nunca se incluyen en las listas de canales o bots.
- Messenger usa `META_APP_SECRET` y `META_APP_ID` como respaldo independiente cuando el canal no tiene secreto o ID propios. `guardarCanalMessenger` acepta `app_secret` y `app_id` opcionales: cifra el secreto en `config.appSecretEncrypted` con la clave existente y guarda el ID en `config.appId`. Omitirlos o enviarlos vacíos conserva lo anterior. Las respuestas y listas solo incluyen campos públicos; el secreto y su cifrado quedan fuera de respuestas y bitácora. No se modifica SQL. Se conserva `META_GRAPH_VERSION`. No hay OAuth ni App Review en este cambio: la conexión guarda el token de página cifrado y suscribe los siete campos solicitados. La disponibilidad real de `HUMAN_AGENT` depende de lo que permita Meta a la app; un rechazo se registra como fallido.
- El webhook usa únicamente `entry[].id` antes de autenticar para resolver la empresa con `resolve_org_by_page` y leer el canal bajo RLS. Cada entrada verifica el cuerpo crudo completo contra su secreto propio o, solo cuando falta, el global. Un secreto cifrado ilegible falla cerrado. Una firma válida para un canal no autoriza otros. Si todas las páginas conocidas rechazan la firma, devuelve 401 sin escrituras ni llamadas a Graph; si alguna autoriza, procesa solo esas entradas y confirma 200. Las páginas desconocidas se ignoran con 200. La firma del sobre no se puede validar por separado contra fragmentos serializados del cuerpo.
- Una página activa solo puede conectarse una vez en todo el CRM. Se consulta `resolve_org_by_page` antes de suscribirla para detectar duplicados entre empresas pese a RLS; editar la misma conexión sigue permitido. El índice `canales_messenger_page_activa_uq` resuelve carreras concurrentes; sus errores `P2002`/`23505` se convierten en 409 «esa página ya está conectada».
- La ventana de Messenger usa `ultimo_entrante_at`, con backfill desde mensajes y actualización monotónica en cada entrada. Bots y automatizaciones solo usan RESPONSE antes de 24 h; un asesor autenticado puede usar HUMAN_AGENT desde 24 h hasta antes de 7 días. Un eco nunca reabre la ventana. `normalizarMessenger` recibe el ID de app explícitamente del webhook o proveedor: usa `appId` del canal y, cuando falta, `META_APP_ID`. Se omiten ecos de esa app para evitar duplicar envíos del CRM; los de otras apps sí se guardan salientes, aunque coincidan con el ID global.
- Adjuntos de Messenger: texto primero y media después. Los archivos locales se comparten con un enlace firmado de 15 minutos, limitado al nombre exacto del archivo y sin cookies. La firma usa la clave existente con un prefijo de propósito específico; no habilita acceso a otros archivos. Sin la firma se conserva la autorización normal de media por empresa. Un mensaje entrante con varios adjuntos conserva el MID en el primero y añade `:adjunto:N` a los siguientes.
- Se amplió la lista inicial de archivos por la necesidad de servir adjuntos a Meta: `web/src/lib/channel/media-publica.ts` y `web/src/app/api/media/[archivo]/route.ts`.
- Revisión final: también se ajustó `web/src/app/api/v1/accounts/[accountId]/conversations/[conversationId]/route.ts` para que GET devuelva el mismo `sender.identifier` externo del webhook. Se conserva la estructura HTTP existente y se añade cobertura a la prueba de API. Se añadió `web/prisma/scripts/test-canales-e2e.ts` como prueba HTTP complementaria; no pudo ejecutarse en esta sesión por el rechazo automático al arranque del servidor local.
- UI: API no tiene ventana; Messenger permite al asesor enviar hasta 7 días y muestra el aviso al cerrar 24 h. Plantillas oficiales y programación existentes se mantienen solo para WhatsApp; no se implementó difusión/programación para los canales nuevos.
- Validación del secreto por canal: [informe del 15-oct-2026](pruebas-messenger-appsecret-2026-10-15.md). TypeScript, build, pruebas de canales base/API/Messenger, aislamiento en 80 tablas, seguridad y ESLint en verde. La prueba HTTP adicional permanece pendiente porque la revisión automática rechazó el arranque del servidor local. No se llamó a Meta ni se tocó producción.
